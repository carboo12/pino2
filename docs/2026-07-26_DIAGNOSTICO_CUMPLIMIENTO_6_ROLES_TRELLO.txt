C0.1 [CRÍTICO] SUPER-ADMIN BLOQUEADO EN NESTJS
-------------------------------------------------------------------------------

Evidencia:

- Se analizaron 224 decoradores @Roles en controllers.
- Cero decoradores contienen super-admin.
- RolesGuard compara igualdad estricta.
- RolesGuard no tiene bypass para super-admin.

Consecuencia:

El usuario admin@multitienda.com con role=super-admin recibe 403 en todos los
endpoints protegidos con @Roles('admin'), incluyendo usuarios, tiendas,
configuración y módulos globales.

Corrección obligatoria:

1. RolesGuard debe permitir super-admin como bypass global.
2. Los endpoints exclusivos globales deben declarar super-admin, no admin.
3. No convertir super-admin a admin para evitar el 403.

Código objetivo:

  const normalizedRole = normalizeUserRole(user.role);
  if (normalizedRole === 'super-admin') return true;
  return requiredRoles.includes(normalizedRole);

Criterio:

- super-admin abre panel global y cualquier tienda.
- super-admin puede crear/editar usuarios.
- super-admin no depende de user_stores.


C0.2 [CRÍTICO] ADMIN FUE CONVERTIDO EN GLOBAL
-------------------------------------------------------------------------------

Evidencia:

StoreAccessGuard permite acceso global cuando role es admin o super-admin.
React MASTER_ROLES contiene ['admin', 'super-admin'].
getRedirectPath envía admin a /master-admin/dashboard.
AppLayout permite admin consultar todas las tiendas.

Esto contradice el modelo acordado:

- admin = Jefe de una bodega.
- super-admin = Administrador General global.

Corrección obligatoria:

Backend:

  if (normalizedRole === 'super-admin') return true;

  // admin también debe validar user.storeIds.

React:

  MASTER_ROLES = ['super-admin'];
  STORE_ADMIN_ROLES = ['admin'];

Redirect:

  super-admin -> /master-admin/dashboard
  admin       -> /store/{primerStoreId}/work/admin

AppLayout:

- Sólo super-admin carga todas las tiendas.
- admin carga únicamente user.storeIds.
- Logo de admin vuelve a su tienda, no al panel global.

Criterio:

El Jefe controla todos los módulos de Los Pinos - Central, pero no puede abrir,
editar ni comparar otra tienda. El Administrador General sí puede hacerlo.

C0.4 [CRÍTICO] FLUTTER NO FUE MIGRADO A LOS 6 ROLES
-------------------------------------------------------------------------------

Evidencia:

flutter/lib/core/utils/role_utils.dart conserva 12 roles legacy.
No reconoce el valor canónico gestor.
No reconoce super-admin.
El usuario role=gestor se convierte en AppRole.unknown.

Consecuencia:

El Gestor activo no recibe las acciones de preventa. La App le ofrece el
fallback de rol desconocido y no puede ejecutar el flujo obligatorio.

Además, el antiguo bloque vendor/salesManager muestra Cobros, Devoluciones,
Stock de carga y Cierre de Caja, acciones expresamente prohibidas al Gestor.

Corrección obligatoria:

  enum AppRole {
    admin,
    superAdmin,
    auxiliar,
    inventory,
    gestor,
    rutero,
    unknown,
  }

normalizeRole debe aceptar primero los 6 valores canónicos. Los aliases sólo se
usan durante transición y nunca se persisten.

Acciones permitidas al Gestor:

- Ruta/visitas asignadas.
- Clientes asignados.
- Preventa por bultos/unidades.
- Catálogo y stock de bodega de sólo lectura.
- CxC y límite de crédito de sólo lectura.
- Sincronización y conflictos de outbox.

Acciones prohibidas al Gestor:

- Cobrar.
- Emitir factura final de entrega.
- Registrar devolución de entrega.
- Ver/administrar inventario de camión.
- Cierre de caja o liquidación.
- Elegir clientes o pedidos fuera de su ruta.

Rutero conserva:

- Carga propia.
- Aceptación de custodia.
- Entrega total/parcial.
- Cobro.
- Rechazo/devolución.
- Impresión.
- Retorno y liquidación.

Criterio:

Login gestor abre la pantalla Preventa. Login rutero abre Ruta de Entrega.
Ninguno recibe acciones del otro.


C0.5 [CRÍTICO] VALIDADORES SQL TODAVÍA EXIGEN ROLES ELIMINADOS
-------------------------------------------------------------------------------

Se detectaron 12 literales legacy funcionales en backend fuera de pruebas.

Casos bloqueantes confirmados:

- ClientsService.reasignarMany valida sales-manager/vendor.
- RoutesService.validateVendor valida sales-manager/vendor/rutero.
- AccountsReceivableService filtra sólo actorRole=sales-manager.
- SyncService reconoce sólo actorRole=sales-manager.

Consecuencias:

- No se puede asignar/reasignar una ruta al usuario role=gestor.
- No se puede ejecutar Reasignación Express hacia el Gestor nuevo.
- El Gestor puede recibir una CxC sin filtro de cartera porque el servicio no
  reconoce actorRole=gestor.
- El delta sync puede descargar datos fuera de la cartera o no descargar la
  cartera correcta.

Correcciones mínimas:

  u.role = 'gestor'

  actorRole === 'gestor'

  u.role IN ('gestor', 'rutero') // sólo donde el responsable puede ser ambos.

No realizar reemplazo ciego de la palabra vendor cuando sea nombre de columna,
vendor_id, DTO o concepto de inventario; sólo cambiar comparaciones de rol.

Criterio:

- Crear ruta SALES con gestor activo funciona.
- Reasignar clientes a gestor activo funciona.
- CxC del Gestor contiene sólo clientes de route_clients.
- Delta sync del Gestor contiene sólo su cartera.
