6.4 Migración de esquema P0

Crear una migración fechada nueva, no editar migraciones ya aplicadas.
Ejemplo base:

  BEGIN;

  ALTER TABLE accounts_receivable
    ADD COLUMN IF NOT EXISTS sale_id uuid REFERENCES sales(id),
    ADD COLUMN IF NOT EXISTS invoice_number varchar(80),
    ADD COLUMN IF NOT EXISTS issued_at timestamptz,
    ADD COLUMN IF NOT EXISTS due_date date,
    ADD COLUMN IF NOT EXISTS credit_days_snapshot integer,
    ADD COLUMN IF NOT EXISTS credit_note_amount numeric(14,2)
      NOT NULL DEFAULT 0;

  UPDATE accounts_receivable
  SET status = CASE upper(coalesce(status, ''))
    WHEN 'ACTIVE' THEN 'PENDING'
    WHEN 'PAID_IN_FULL' THEN 'PAID'
    WHEN 'OVERDUE' THEN 'PENDING'
    ELSE upper(status)
  END;

  ALTER TABLE accounts_receivable
    ALTER COLUMN status SET DEFAULT 'PENDING';

  CREATE UNIQUE INDEX IF NOT EXISTS uq_ar_sale
    ON accounts_receivable(sale_id)
    WHERE sale_id IS NOT NULL;

  CREATE UNIQUE INDEX IF NOT EXISTS uq_ar_order
    ON accounts_receivable(order_id)
    WHERE order_id IS NOT NULL;

  CREATE INDEX IF NOT EXISTS idx_ar_store_due_pending
    ON accounts_receivable(store_id, due_date)
    WHERE remaining_amount > 0;

  CREATE INDEX IF NOT EXISTS idx_ar_client_pending
    ON accounts_receivable(client_id, due_date)
    WHERE remaining_amount > 0;

  COMMIT;

Luego agregar constraints mediante bloque DO para permitir re-ejecución segura:

- credit_days_snapshot >= 0.
- total_amount >= 0.
- remaining_amount entre 0 y total_amount.
- credit_note_amount entre 0 y total_amount.
- status IN ('PENDING','PARTIAL','PAID','CANCELLED').
- Debe existir sale_id u order_id para cuentas nuevas.

7.3 Refactor obligatorio de factura de compra

Orden correcto dentro de una sola transacción:

1. Validar proveedor y tienda.
2. Validar número de factura único por proveedor/tienda.
3. Resolver todos los productos.
4. Calcular subtotal de cada línea.
5. Calcular total en backend.
6. Insertar invoices con calculatedTotal.
7. Insertar todos los invoice_items, incluso productos recién creados.
8. Actualizar stock por producto con FOR UPDATE.
9. Insertar movements con costo y referencia.
10. Si pago=CREDITO, crear accounts_payable con calculatedTotal.
11. Si pago=CONTADO, no crear CxP.
12. Commit.

Código crítico:

  const preparedItems = [];

  for (const item of dto.items) {
    const productId = item.productId
      ?? await resolveOrCreateProduct(client, dto.storeId, item);

    preparedItems.push({
      ...item,
      productId,
      subtotal: item.quantity * item.unitPrice,
    });
  }

  const calculatedTotal = preparedItems.reduce(
    (sum, item) => sum + item.subtotal,
    0,
  );

  const invoice = await insertInvoice(client, {
    ...dto,

  for (const item of preparedItems) {
    await insertInvoiceItem(client, invoice.id, item);

  }

  if (isCredit(dto.paymentType)) {
    await insertAccountPayable(client, {
      invoiceId: invoice.id,
      totalAmount: calculatedTotal,
      remainingAmount: calculatedTotal,
      dueDate: dto.dueDate,
    });
  }

7.5 Nota de crédito de proveedor

Regla:

Una nota de crédito de proveedor representa productos devueltos de una factura
de compra. Debe:

- reducir el inventario;
- reducir el saldo a pagar;
- conservar número/fecha/motivo;
- conservar items y cantidades;
- no permitir devolver más de lo comprado menos lo ya devuelto;
- poder aplicarse total o parcialmente a una CxP.

Tablas nuevas recomendadas:

  supplier_credit_notes
  ---------------------
  id uuid PK
  store_id uuid FK
  supplier_id uuid FK
  invoice_id uuid FK
  account_payable_id uuid FK
  credit_note_number varchar(80)
  issue_date date
  total_amount numeric(14,2)
  applied_amount numeric(14,2)
  status varchar(20) -- DRAFT, POSTED, APPLIED, CANCELLED
  reason text
  created_by uuid
  created_at timestamptz

  supplier_credit_note_items
  --------------------------
  id uuid PK
  credit_note_id uuid FK
  invoice_item_id uuid FK
  product_id uuid FK
  quantity numeric
  unit_cost numeric(14,2)
  subtotal numeric(14,2)

  payable_adjustments
  -------------------
  id uuid PK
  account_payable_id uuid FK
  source_type varchar(30) -- SUPPLIER_CREDIT_NOTE
  source_id uuid
  amount numeric(14,2)
  created_at timestamptz

Índices/únicos:

- unique(store_id, supplier_id, credit_note_number)
- index(account_payable_id, status)
- index(invoice_id)
- unique(source_type, source_id, account_payable_id)

7.6 Transacción crítica de nota de crédito

Pseudocódigo obligatorio:

  return db.withTransaction(async (client) => {
    const payable = await lockPayable(client, dto.accountPayableId);
    const invoice = await lockInvoice(client, dto.invoiceId);

    const preparedItems = await validateReturnableQuantities(
      client,
      invoice.id,
      dto.items,

    const creditTotal = sum(preparedItems.subtotal);

      throw new BadRequestException(
        'La nota no puede superar el saldo pendiente'

16. CRITERIO FINAL DE CORTE
===============================================================================

NO cambiar la base activa si cualquiera de estas condiciones sigue presente:

- clientes legacy visibles <= 1 sin decisión de negocio;
- faltan usuarios recientes;
- faltan productos recientes;
- faltan ventas/pedidos recientes;
- CxC sigue sin due_date;
- venta a crédito no guarda client_id;
- venta a crédito no crea CxC;
- InvoicesService conserva el continue del producto nuevo;
- una factura puede borrarse sin reversión;
- nota de crédito de proveedor no reduce CxP de forma transaccional;
- existen huérfanos o diferencias de sumas.

CAMBIO APROBABLE:

sistema_de_inventario puede convertirse en DATABASE_NAME principal cuando:

1. Histórico y operación reciente estén unidos.
2. Los clientes estén visibles correctamente.
3. Los contratos SQL de NestJS coincidan con el esquema real.
4. CxC implemente plazo de 8 días y excepciones.
5. CxP use factura, vencimiento y notas de crédito.
6. Las tres vías de entrada de inventario generen trazabilidad.
7. React permita operar los flujos sin rutas ocultas ni botones ficticios.
8. Flutter pueda cobrar CxC con vencimiento e idempotencia.
