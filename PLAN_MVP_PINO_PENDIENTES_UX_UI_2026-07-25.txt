===============================================================================
0. ALCANCE OBLIGATORIO
===============================================================================

Este plan cubre únicamente:

- Integridad funcional necesaria para un MVP.
- Backend NestJS y contratos de datos que afectan los flujos operativos.
- Web React, con prioridad máxima en UX, HTML y CSS.
- Flutter únicamente donde afecta el flujo MVP y la sincronización.
- PostgreSQL únicamente donde afecta consistencia y funcionamiento.
- Navegación, formularios, tablas, caja/POS, bodega, catálogo y finanzas.

Fuera de alcance por decisión del propietario:

- Seguridad.
- CI/CD.
- Despliegue.
- Documentación general.
- Creación o ampliación de suites de pruebas.

REGLA PARA EL AGENTE:
No expandir el alcance hacia los puntos excluidos. No reescribir el sistema, no
cambiar de stack y no dividirlo en microservicios.

===============================================================================
1. VEREDICTO DIRECTO
===============================================================================

PUNTUACIÓN GLOBAL ACTUAL COMO MVP COMPLETO: 5.2 / 10

Interpretación:

- 1 a 3: prototipo incompleto.
- 4 a 5: demostrable, pero todavía riesgoso para operación real.
- 6 a 7: MVP utilizable en operación controlada.
- 8 a 9: producto estable y consistente.
- 10: producto maduro.

Pino está en la parte alta de "demostrable", pero aún no alcanza "MVP utilizable
en operación controlada" porque existen fallos funcionales capaces de:

- perder operaciones offline;
- mostrar una venta exitosa aunque el backend la rechace;
- enviar métodos de pago que el backend no acepta;
- borrar una operación local sin confirmación válida del servidor;
- dejar rutas visibles que redirigen a una pantalla inexistente;
- mostrar que la caja está cerrada cuando ya existe un turno activo;
- limitar la sincronización móvil a una sola página;
- avanzar el cursor móvil antes de terminar de guardar los datos;
- calcular o representar mal productos por bulto en el carrito web.

PUNTUACIÓN POR ÁREA

[6.8/10] Arquitectura general
Base modular razonable. Mantener monolito NestJS, SPA React y app Flutter.
No crear microservicios, micro-frontends ni un BFF desplegado por separado.

[6.6/10] Backend NestJS
La reciente separación en repositorios, mappers y casos de uso es positiva.
Compila sin errores. Todavía hay idempotencia duplicada, promociones que fallan
silenciosamente, contratos incompletos y estados no completamente unificados.

[5.8/10] PostgreSQL y consistencia de datos
Modelo amplio y útil, pero el historial de migraciones y el esquema visible no
son una fuente totalmente confiable. Hay fuentes de verdad duplicadas.

[5.7/10] Web React funcional
Compila sin errores y la carga diferida está bien encaminada. Aún mezcla varios
patrones de datos y conserva pantallas duplicadas o contradictorias.

[4.4/10] UX/UI web
La base visual es limpia, pero falta un sistema operacional coherente. Hay 370
usos de colores hexadecimales directos, 38 colores únicos y 70 textos de 10 u
11 px. Las páginas cambian demasiado de estilo y varias acciones táctiles son
demasiado pequeñas.

[4.0/10] Caja/POS web
Es el flujo más importante y todavía tiene contradicciones graves: búsqueda no
conectada, pago con estados falsos, método incompatible con el DTO, carrito sin
modelo explícito de bultos y estado visual incorrecto de caja.

[2.6/10] Offline y sincronización web
No es confiable. Se serializa una función con toString(), el cliente y servidor
no usan la misma clave de resultado y se puede borrar una operación local sin
haber sido aplicada.

[4.8/10] Flutter
La estructura Riverpod/Drift es recuperable y el router mejoró. El delta sync
todavía no persiste varias entidades, no espera todas las escrituras y depende
de un totalCount que el backend no entrega.

[6.0/10] Mantenibilidad
Hay mejoras recientes, pero siguen existiendo muchos any, estilos directos,
interfaces duplicadas y componentes/páginas que implementan el mismo flujo de
formas diferentes.

META PARA DECLARARLO MVP: 7.0 / 10

Para llegar a 7.0 no hace falta terminar todos los módulos. Hace falta:

1. Venta online correcta y sin mensajes falsos.
2. Operaciones offline que nunca se eliminen sin acuse positivo.
3. Estados de pedidos y caja coherentes.
4. Navegación sin enlaces muertos.
5. Interfaz legible, rápida y consistente en escritorio, tablet y móvil.
6. Formularios y tablas con un patrón común.
7. Esquema/migraciones alineados con el código que realmente se ejecuta.

[ ] Mostrar éxito solamente desde CashWorkspace después de la respuesta válida.
[ ] Si falla, mantener abierto el diálogo y conservar carrito/monto.
[ ] Bloquear doble clic mientras se procesa.

5.1 NO SERIALIZAR FUNCIONES

Problema crítico:
useOfflineOperation guarda operation.toString(). El DTO exige data como objeto.
Una función convertida a texto no es una operación reproducible.

Checklist:

[ ] Cambiar execute(() => Promise) por execute(data).
[ ] Guardar endpoint lógico o type más payload JSON puro.
[ ] Validar que data sea serializable antes de persistir.
[ ] Generar operationId una sola vez.
[ ] Conservar operationId en cada reintento.

Contrato canónico:

type SyncOperationType =
  | 'SALE'
  | 'ORDER'
  | 'COLLECTION'
  | 'RETURN';

interface PendingOperation<T extends Record<string, unknown>> {
  id: string;
  operationId: string;
  storeId: string;
  type: SyncOperationType;
  data: T;
  status: 'pending' | 'processing' | 'failed';
  retryCount: number;
  createdAt: number;
  nextAttemptAt: number;
  lastError?: string;
}

Firma correcta:

execute: (data: Record<string, unknown>) => Promise<{
  queued: boolean;
  operationId: string;
}>;

5.2 RESPUESTA DE BATCH INCONSISTENTE

Problema crítico:
Backend responde con opId y estado SUCCESS/FAILED. Web busca operationId y espera
APPLIED/DUPLICATE. Además, si no encuentra resultado, elimina la operación:

if (!result || result.status === 'APPLIED' || result.status === 'DUPLICATE')

Eso convierte una respuesta desconocida en éxito y puede perder datos.

Decisión obligatoria:
Backend y clientes usarán exactamente:

interface SyncResult {
  operationId: string;
  status: 'APPLIED' | 'DUPLICATE' | 'FAILED';
  serverId?: string;
  errorCode?: string;
  errorMessage?: string;
}

Checklist backend:

[ ] Cambiar opId por operationId en toda respuesta.
[ ] Cambiar SUCCESS por APPLIED.
[ ] Usar DUPLICATE explícito.
[ ] Conservar FAILED.
[ ] Devolver siempre un resultado por cada operación recibida.

Checklist web:

[ ] Solo borrar IndexedDB en APPLIED o DUPLICATE.
[ ] Si no existe resultado, marcar failed y conservar.
[ ] Si status es desconocido, marcar failed y conservar.
[ ] Guardar errorCode y errorMessage.
[ ] No borrar lotes completos por HTTP 200.

CÓDIGO WEB OBLIGATORIO:

const result = results.find(
  (candidate) => candidate.operationId === operation.operationId,
);

if (!result) {
  await indexedDBService.updateOperationStatus(
    operation.id,
    'failed',
    'El servidor no devolvió confirmación para esta operación',
  );
  continue;
}

if (result.status === 'APPLIED' || result.status === 'DUPLICATE') {
  await indexedDBService.removePendingOperation(operation.id);
  continue;
}

await indexedDBService.updateOperationStatus(
  operation.id,
  'failed',
  result.errorMessage ?? 'La operación fue rechazada',
);

5.3 DOBLE CLAIM DE IDEMPOTENCIA EN VENTA OFFLINE

Problema crítico:
SyncService reclama operationId con InboxService antes de abrir la transacción.
Después ProcessSaleUseCase intenta insertar el mismo operationId en sync_inbox.
La venta puede interpretarse como duplicada antes de haberse procesado.

Decisión:
El flujo batch es dueño del claim. El caso de uso no debe reclamar otra vez
cuando se ejecuta desde batch.

Estructura recomendada:

interface OperationContext {
  operationId: string;
  inboxAlreadyClaimed: boolean;
}

await db.withTransaction(async (client) => {
  const claim = await inboxRepository.claim(client, envelope);

  if (!claim.claimed) {
    return duplicateResult(claim.existingResult);
  }

  const sale = await processSaleUseCase.execute(
    saleDto,
    userId,
    client,
    {
      operationId: envelope.operationId,
      inboxAlreadyClaimed: true,
    },
  );

  await inboxRepository.markProcessed(
    client,
    envelope.storeId,
    envelope.operationId,
    sale,
  );

  return sale;
});

Checklist:

[ ] InboxRepository debe aceptar PoolClient.
[ ] claim, operación y markProcessed deben compartir transacción.
[ ] El endpoint directo /sales/process puede hacer su propio claim.
[ ] El batch no debe llamar un segundo claim.
[ ] Un registro PROCESSING antiguo no equivale automáticamente a DUPLICATE
    aplicado; distinguir IN_PROGRESS, PROCESSED y FAILED.

5.4 REINTENTOS

[ ] Agregar nextAttemptAt a IndexedDB.
[ ] No reintentar inmediatamente en ciclo infinito.
[ ] Backoff: 2 s, 5 s, 15 s, 30 s, 60 s, máximo 5 min.
[ ] Las operaciones de una misma tienda se procesan por orden de creación.
[ ] No procesar dos ventas del mismo turno en paralelo.
[ ] Mostrar al usuario: "Guardado sin conexión" y cantidad pendiente.
[ ] Si falla definitivamente, mostrar acción "Revisar", no borrar.

6. P0-C — DELTA SYNC FLUTTER/BACKEND
===============================================================================

Archivos:

- backend/src/modules/sync/sync.service.ts
- flutter/lib/core/network/delta_sync_service.dart
- flutter/lib/core/database/app_database.dart
- flutter/lib/core/database/local_cache_repository.dart

Problemas actuales:

1. Flutter espera totalCount, pero backend no lo devuelve.
2. Por defecto totalCount=0 y el ciclo termina después de la primera página.
3. Flutter llama _processEntity(...) sin await.
4. Varias entidades tienen handlers vacíos.
5. Backend aplica un mismo offset a tablas independientes.
6. Un timestamp global no es un cursor seguro para múltiples tablas.
7. El backend usa updated_at/created_at de forma genérica aunque no todas las
   tablas garantizan ambas columnas.

Decisión MVP:
Usar cursor por entidad y por tienda. No usar un offset común para nueve tablas.

Respuesta recomendada:

{
  "serverTime": "2026-07-25T12:00:00.000Z",
  "entities": {
    "products": {
      "items": [],
      "nextCursor": "2026-07-25T11:58:00.000Z|uuid",
      "hasMore": false
    },
    "clients": {
      "items": [],
      "nextCursor": "...",
      "hasMore": false
    }
  }
}

Orden MVP de entidades:

[ ] products
[ ] productBarcodes
[ ] clients
[ ] receivables
[ ] routes
[ ] deliveries

No incluir una entidad en la respuesta si Flutter no la persiste ni la usa.

Checklist Flutter:

[ ] Agregar await delante de cada _processEntity.
[ ] Eliminar handlers vacíos.
[ ] Implementar upsert real por entidad.
[ ] Guardar cursor después del commit local.
[ ] Guardar cursor por storeId + entityName.
[ ] Si una entidad falla, no avanzar su cursor.
[ ] Procesar tombstones para bajas.
[ ] No reemplazar todo el catálogo ante cada delta.
[ ] Conservar queue de escritura separada del delta de lectura.
